# AGENTS.md — V-Shape Workout Tracker

## Mission
Build a mobile-first PWA that helps a user follow and track a four-day dumbbell-only V-shape workout program. The app must be fast to use during a workout and safe with user data.

## Read Before Coding
1. `.specify/memory/constitution.md`
2. `specs/001-mvp/spec.md`
3. `specs/001-mvp/plan.md`
4. `docs/architecture.md`
5. `docs/domain-model.md`
6. `docs/ux-ui.md`
7. `docs/workout-program.md`

## Hard Product Constraints
- MVP equipment: dumbbells + floor + bodyweight only.
- No band, bench, machine, pull-up bar, or mounted equipment in the default program.
- Four training days: Monday, Tuesday, Thursday, Saturday.
- Direct abs training occurs on Tuesday and Saturday.
- Workout logging must capture sets, reps, weight, optional RIR, and completion.
- Mobile-first; primary use case is one-handed use between sets.
- Progress photos are private by default and must never be publicly addressable.

## Engineering Rules
- TypeScript strict mode. Avoid `any` unless justified in code comments.
- Prefer Server Components for read-heavy screens; use Client Components only when interactivity requires them.
- Keep domain logic in `lib/`, not inside page components.
- Supabase tables that contain user data require RLS before feature completion.
- Do not use the service-role key in browser code.
- Every new user-facing feature needs at least one relevant automated test.
- Any schema change must include a migration.
- Do not add NestJS in MVP unless an ADR proves Next.js + Supabase cannot meet the requirement.
- Avoid introducing new dependencies when platform/browser APIs are sufficient.

## Fitness Content Guardrail
Exercise form content is user-facing fitness guidance. Do not invent biomechanics. Changes to exercise instructions, cues, target muscles, or exercise substitutions must be reviewed against reputable training/clinical references before being marked production-ready. Images generated by AI are illustrations only and require form review before release.

## AI Workflow
For every feature:
1. Read the relevant spec and acceptance criteria.
2. State assumptions only when needed; prefer existing project decisions.
3. Implement the smallest complete vertical slice.
4. Add/update tests.
5. Run `pnpm check` and relevant Playwright tests.
6. Update docs/spec/tasks when behavior or decisions change.
7. Prepare a focused PR; do not mix unrelated refactors.

## Parallel Work
Use separate branches/worktrees for independent features. Do not let two agents edit the same schema migration or central program file concurrently without coordination.

Suggested ownership:
- Agent A: workout session + set logging
- Agent B: progress + measurements/charts
- Agent C: exercise library + form guidance
- Agent D: auth + profile + storage/RLS
